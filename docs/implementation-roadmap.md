# AgentLife 第一版实现步骤规划

## 1. 文档目的

本文把现有产品级详细设计整理为可执行的第一版工程路线图，明确实现顺序、阶段交付物、技术基线、验证门槛和暂缓范围。

本文是实施规划，不代表任何阶段已经实现。各领域产品语义仍以对应详细设计文档为准；当本规划与领域设计冲突时，应先修订规划或补充设计，不能由实现自行改变产品语义。

## 2. 第一版目标

第一版提供一个本地、单用户、纯文字的 MUD 式体验：

* 一个用户正常实体、一个主要 AI 正常实体和少量降级实体共同存在于小型虚构世界。
* 地点、人物、物品、感知、对话和动作结果均以文字表达。
* 用户通过自然语言参与世界，也可以使用独立的管理命令控制模拟、保存和诊断。
* AI 伙伴只能依据 Identity、身体状态、有限感知、当前认知和获准记忆形成决定。
* 世界、身体、行为树和确定性规则按固定 Tick 运行；模型和用户等待期间模拟时间不推进。
* 静态内容便于人工创作和版本管理，动态状态能够原子保存、恢复和审计。

第一版优先证明持续生活闭环、主观信息边界和时间调度语义，不追求大规模内容、复杂物理或生产级分布式部署。

## 3. 推荐技术基线

### 3.1 总体形态

采用 TypeScript、Node.js 24 和单进程模块化单体。领域模块之间通过明确接口协作，不通过数据库表或共享可变对象绕过权限边界。

模型及 Agent 基础能力优先复用：

* `@earendil-works/pi-ai`：模型供应商、鉴权、流式响应和用量信息。
* `@earendil-works/pi-agent-core`：有状态 Agent、工具调用和生命周期事件。
* `@earendil-works/pi-tui`：终端组件、固定布局、滚动区、输入和 Overlay。

AgentLife 自行实现世界、身体、感知、认知、记忆、规则权限和模拟调度。Pi 的会话和原始模型响应只作为受保护诊断，不能替代角色认知或主观记忆。

### 3.2 建议复用的组件

* TypeBox：配置、领域提交和 Agent 工具参数的运行时结构验证。
* YAML：目录化内容包的主要结构化格式。
* SQLite：本地运行状态、快照、阶段记录、事件和记忆索引。
* Drizzle ORM：稳定表结构、迁移和类型化查询；不采用传统 ORM 实体建模驱动领域设计。
* Mistreevous：降级实体行为树，通过适配层禁用真实时间、未授权函数和非确定性行为。
* Vitest：少量关键不变量和冒烟测试。

所有依赖在工程初始化时固定具体版本并提交 lockfile。升级依赖必须重新执行相应适配验证，不能默认新版本保持领域语义。

## 4. 用户界面规划

### 4.1 首选 TUI

Pi TUI 已具备全屏视口、横纵布局、滚动区、焦点管理和 Overlay，第一版优先实现 TUI，不同时维护 Web 前端。

宽屏布局如下：

```text
┌ 时间 / 模式 / 配置版本 / 屏障状态 ─────────────────────────┐
│ 当前所在地与环境描述             │ 同地点实体与物品          │
│                                  │ > AI 伙伴                 │
│                                  │   降级实体                │
├──────────────────────────────────┴───────────────────────────┤
│                    可滚动交互与事件日志                       │
│ 玩家发言、角色表达、动作结果、系统提示、等待状态              │
├──────────────────────────────────────────────────────────────┤
│ > 自然语言输入                                      [状态]    │
└──────────────────────────────────────────────────────────────┘
```

固定区域职责：

* 顶栏显示模拟时间、Tick、运行模式、配置版本、屏障和模型工作状态。
* 地点区只显示用户角色当前能够感知的地点及环境。
* 实体区只显示同地点且能够被用户角色感知的人物与物品。
* 日志区显示对话、动作结果、观察变化和必要系统消息。
* 输入区接收自然语言；斜杠命令进入受保护的管理入口。

宽度达到 120 列时使用完整分栏。较窄终端切换为“地点 / 实体 / 日志”标签页，输入栏保持固定。

### 4.2 管理监视面板

`F2` 或 `/monitor` 打开覆盖式监视面板，第一版包含：

* **Entities：** 实体位置、能力层级、身体指标、动作和调度状态。
* **World：** 地点、物品关系、世界过程和近期客观事件。
* **Scheduler：** Tick 阶段、活动索引、屏障、待处理请求和 Fast Forward 状态。
* **Memory：** 各角色记忆层数量、索引状态和检索诊断；默认不展示完整私密文本。
* **Diagnostics：** 配置版本、模型调用、失败和阶段追踪。

监视面板必须醒目标记为管理员视图。其内容不能进入用户角色观察、认知上下文或记忆。

### 4.3 TUI/Web 决策门

阶段 0 必须在 Windows Terminal 中验证中文输入法、窗口缩放、固定布局、滚动、Overlay 焦点和模型流式输出。

只有存在无法规避的输入或焦点阻断问题时才切换为本地 Web。回退方案固定为 Fastify、WebSocket 和 React/Vite，并复用相同应用服务接口，不重写模拟内核。

## 5. 内容与持久化规划

### 5.1 目录化静态内容

世界及角色设计资料使用目录化 YAML/Markdown：

```text
content/<pack>/
  manifest.yaml
  world/
  locations/
  characters/
  bodies/
  items/
  rules/
  behaviors/
  prompts/
  texts/
```

短文本直接保存在 YAML 多行字段中。长篇内容可以通过受控相对引用关联 Markdown；引用必须留在当前内容包目录内，并参与内容包完整性身份计算。

静态文件负责定义、候选、导入和导出。内容加载并编译后，运行时不能把这些文件当作可变权威状态。

### 5.2 SQLite 动态运行状态

SQLite 保存：

* 当前世界、身体、人物和调度状态。
* Tick 阶段记录、幂等提交和屏障状态。
* Recent/Long-term Memory、主观实体档案及其索引。
* 快照、时间线、配置版本引用和迟到响应隔离信息。
* 客观事件与受保护诊断。

SQLite 只为稳定且经常筛选的内容建立列，例如 ID、所有者、领域、类型、Tick、时间线、版本、生命周期状态和来源类型。

仍可能变化的领域内容采用以下语义保存为规范化 JSON TEXT：

```ts
interface VersionedPayload {
  schemaVersion: string;
  type: string;
  data: unknown;
}
```

每次读写均按 `schemaVersion` 使用对应 TypeBox Schema 验证。只有已经稳定且存在明确查询需求的字段才提升为正式列或表达式索引，避免在产品语义仍变化时过度关系化。

### 5.3 快照、日志与恢复

* 安全保存边界写入完整规范化快照。
* 同一事务追加阶段完成记录、事件和配置版本引用。
* 快照是恢复基线；事件日志仅用于事实检查和故障定位，第一版不实现完整事件溯源。
* 从旧快照恢复时生成新的时间线身份，旧时间线后续响应和提交均失效。
* 导入、导出可以产生可阅读的目录化 JSON/Markdown，但导出物不是运行时权威状态。

## 6. 记忆检索与向量策略

### 6.1 第一版不引入专用向量数据库

第一版按以下顺序检索：

1. SQLite 按角色归属、状态、类型、时间和实体关联筛选合法候选。
2. 计算结构关联、关联图、文本匹配和当前情境分数。
3. 读取有限候选的 embedding，在进程内计算余弦相似度。
4. 与基础可达性及抑制组合为综合激活。
5. 仅把超过门槛的有限结果交给记忆 Agent 重排。
6. 重排结果继续接受 Working Memory 容量准入。

embedding 记录至少包含记忆 ID、提供器、模型、表示版本、维度、向量 BLOB 和内容摘要哈希。不同表示版本不能在一次查询中混用。

### 6.2 后续升级门槛

只有性能测量证明进程内比较已经成为实际瓶颈时才升级：

1. 优先评估 SQLite 内向量扩展。
2. SQLite 扩展仍不能满足规模或延迟要求时，再引入独立向量数据库。
3. 外部向量库只保存可重建派生索引；原始记忆、来源、权限和生命周期仍由 SQLite 掌管。

## 7. 模块和接口边界

第一版按以下模块组织：

* `ContentPackLoader`：加载 YAML/Markdown、限制引用范围并计算内容身份。
* `ConfigurationRegistry`：共享验证、领域验证、编译和原子配置切换。
* `DeterministicRuleKernel`：受限条件、映射、组合、索引和追踪。
* `WorldService`：地点、实体、物品、过程、客观事实和事件。
* `CharacterService`：能力层级、控制来源、主要标记和子系统关联。
* `BodyService`：能力、资源、指标、身体过程和动作生命周期。
* `PerceptionService`：客观材料到观察者私有观察的转换。
* `MemoryService`：Working、Recent、Long-term Memory、档案和检索。
* `CognitionService`：注意、理解、疑问、意图、决定和等待边界。
* `SimulationOrchestrator`：唯一时钟、Tick、屏障、运行模式和恢复。
* `AgentRuntime`：Pi Agent、模型供应商、取消、重试和迟到响应隔离。
* `TerminalApplication`：TUI 组合、用户输入和管理视图。
* `RuntimeStore`：SQLite 事务、快照、事件、记忆和诊断。

Pi 认知 Agent 只暴露两个领域工具：

* `memory_search`：提交 Retrieval Intent，返回经过权限、激活和容量限制的片段。
* `submit_cognitive_decision`：提交认知变化、意图操作、表达、短身体计划、记忆消费、编码候选、档案断言和空闲边界。

Pi 不获得文件、Shell、数据库或世界直接写入能力。

## 8. 实施阶段

### 8.1 阶段 0：技术 Spike

目标是消除组件集成风险，不实现完整玩法。

任务：

* 验证 Pi Agent 自定义工具、流式事件、取消、超时和迟到响应。
* 验证 Pi TUI 固定分栏、响应式标签页、中文输入、日志滚动和监视 Overlay。
* 验证内容包加载、目录逃逸拦截和完整性身份。
* 验证 SQLite JSON 载荷、事务快照和崩溃恢复。
* 验证 Mistreevous 使用模拟 Tick、白名单节点和可保存状态。

交付物：组件适配结论、风险记录和最终 TUI/Web 决定。

退出条件：所有关键组件都能满足权限、确定性和恢复约束；否则在本阶段替换组件或触发已定义的 Web 回退。

### 8.2 阶段 1：内容、配置和规则基础

任务：

* 建立内容包规范和最小演示内容。
* 实现类型、引用、依赖、组合、权限、领域和兼容性验证。
* 编译不可变运行配置、触发索引和稳定求值顺序。
* 实现阈值、分段常量、分段线性及优先级、最小、最大、加法和乘法组合。
* 建立 SQLite 初始迁移、版本化 JSON 载荷和存档接口。

退出条件：演示内容能够生成唯一配置身份；相同配置、输入快照和模拟时间产生相同规则结果与追踪。

### 8.3 阶段 2：确定性模拟内核

任务：

* 实现地点、动态实体、物品关系、环境状态和世界过程。
* 实现普通动态、降级和正常实体，以及独立的主要实体标记。
* 实现说话、移动、手势、拿取、放置和简单物品操作。
* 实现能力、资源、指标、并行冲突、失败和中断。
* 实现完整十二阶段 Tick，新计划从下一 Tick 开始推进。
* 接入受限行为树适配器。
* 实现稳定边界保存、加载和阶段续做。

退出条件：无 LLM 时可以逐 Tick 推进演示世界，动作、资源冲突、行为树计划和世界裁定均可追踪。

### 8.4 阶段 3：可玩 TUI 竖切

任务：

* 完成顶栏、地点、实体、日志和输入固定区块。
* 完成响应式窄屏标签页和管理监视面板。
* 实现地点、人物、物品和动作结果的文字渲染。
* 提供 `/step`、`/run`、`/pause`、`/save`、`/load`、`/status` 和 `/monitor`。
* 使用诊断动作命令验证移动、拿取、放置和世界反馈。

退出条件：用户可以在无 LLM 条件下探索演示世界，普通视图和管理员视图保持信息隔离。

### 8.5 阶段 4：感知与 Pi 认知

任务：

* 实现感知可达性、通道、显著度、分辨率、连续观察和身份关联。
* 用户界面切换为只消费用户角色的授权观察。
* 接入 AI 认知 Agent、用户输入解释 Agent 和全局认知屏障。
* 实现注意、主观理解、疑问、多条意图、持续决定和空闲契约。
* 批量交接同一认知轮次计划，禁止模型返回顺序产生优先级。
* 普通自然语言成为正式角色输入，诊断动作命令只在管理模式保留。

退出条件：用户和 AI 可以通过自然语言交谈并共同活动；模型等待期间世界冻结；AI 输出必须经过身体和世界验证。

### 8.6 阶段 5：主观记忆闭环

任务：

* 实现 Working Memory 容量、替换、消费确认和快速衰减。
* 实现 Recent Memory 选择性编码、时间窗口、到期删除和归档。
* 实现 Long-term Memory 巩固、来源迁移和主观实体档案。
* 实现结构、关联、语义、情境、可达性和抑制组合检索。
* 接入 embedding 提供器和进程内向量比较。
* 实现语义表示版本检查、索引重建和归档隔离。

退出条件：AI 能有限回忆共同经历；冲突认识可以并存；未感知、未使用或已归档内容不能回流。

### 8.7 阶段 6：Fast Forward 与故障恢复

任务：

* 实现单步、连续、暂停、静止和零 LLM Fast Forward。
* 实现主要实体恢复检查和退出快进。
* 实现规则解析屏障优先于认知屏障。
* 实现幂等提交、失败续做、迟到响应隔离和时间线分叉。
* 保证非主要正常实体在快进中不形成或补写主观经历。

退出条件：相同 Tick 数的手动推进和 Fast Forward 产生相同确定性结果；恢复不会重复应用已提交效果。

### 8.8 阶段 7：配置生成 Skill

任务：

* 实现初始配置生成与初始记忆提取两个独立模式。
* 输出目录化候选包、来源、依赖、冲突、阻塞分区和结构化诊断。
* 复用既有验证器进行非权威预检。
* 支持依据外部诊断生成新修订候选。

退出条件：候选生成、失败或重试均不修改内容包和当前运行状态；配置候选与记忆候选严格分离。

## 9. 演示内容范围

首个完整演示包至少包含：

* 三至五个相连地点，并具有不同感知条件。
* 一个用户正常实体和一个主要 AI 正常实体。
* 两个具有不同确定性行为树的降级实体。
* 可携带物、放置面或容器，以及至少一个可操作物品。
* 会产生资源冲突的并行动作。
* 体力、身体完整度和唤醒能力模板。
* 睡眠、外部刺激恢复、长动作中断和 Fast Forward 场景。
* 一段可被选择性编码并在之后影响行动的共同经历。

演示内容只用于验证通用系统，不得把具体地点、角色或规则硬编码进领域模块。

## 10. 最小测试策略

设计仍可能变化，因此不以高覆盖率或大量字段级单元测试为目标。自动测试只保护以下稳定不变量：

1. **配置冒烟：** 演示内容包能够加载、验证并生成稳定配置身份。
2. **Tick 核心：** 移动、资源冲突和世界裁定按固定阶段推进，新计划从下一 Tick 生效。
3. **屏障冻结：** 等待 AI 或用户时模拟时间、动作和身体过程不推进，迟到响应不能提交。
4. **存档恢复：** 保存恢复得到相同稳定状态，重复续做不会重复应用效果。
5. **信息隔离：** Ground Truth、其他角色内部状态、审计归档和原始模型响应不能进入普通认知上下文。

另维护一条使用脚本化假 Agent 的端到端冒烟流程：

```text
进入地点 → 看见 AI 伙伴 → 对话 → 共同移动
→ 拿取物品 → 形成近期记忆 → 保存 → 恢复 → 再次提及经历
```

真实模型测试不进入普通 CI。Fast Forward 等价性先通过人工诊断命令验证，相关语义稳定后再提升为自动回归测试。

## 11. 第一版完成标准

* TUI 固定区块、滚动日志、中文输入和监视面板稳定可用。
* 用户能够通过自然语言与 AI 伙伴交流并共同活动。
* 普通界面只展示用户角色可以感知的信息。
* AI 只能依据获准的感知、认知和记忆形成决定。
* 静态内容可以通过目录化文本进行版本管理。
* 动态状态能够原子保存和恢复，不依赖重新解释源内容文件。
* 角色能够选择性形成、检索、巩固和遗忘记忆。
* 演示规模下无需专用向量数据库即可完成语义检索。
* 降级实体和 Fast Forward 均不调用 LLM。
* 五组核心测试和端到端冒烟流程通过。

## 12. 暂缓范围

第一版不实现：

* 联网 MUD、多用户账户、多人权限和远程服务器。
* 同时维护 TUI 与 Web 两套正式前端。
* 微服务、消息队列、分布式 Tick 和云部署。
* 复杂物理、完整生理、死亡和永久退出。
* 大规模世界生成和复杂多角色社会。
* 专用向量数据库。
* 配置候选审阅、批准、发布和回滚界面。
* 自研行为树编辑器、模型 SDK 或通用 Agent 框架。

## 13. 固定实施原则

1. 静态设计资料以目录文件为权威，动态运行状态以 SQLite 为权威。
2. 未稳定领域字段使用版本化 JSON，不提前关系化。
3. 世界事实、角色感知、认知、记忆和诊断始终分离。
4. LLM 只形成候选决定，不能直接修改世界或身体状态。
5. 模型供应商、模型和 embedding 提供器通过配置选择，不写入领域逻辑。
6. 专用向量数据库必须由实际性能数据触发，不能作为第一版前置依赖。
7. 测试优先保护跨系统不变量，不追求内部实现覆盖率。
8. 每个阶段先达到退出条件，再进入依赖它的下一阶段。
